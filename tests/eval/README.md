# E2E Evaluation Dataset

This directory contains the evaluation infrastructure for benchmarking Quilto agent quality against baseline responses using LLM-as-judge methodology.

## Directory Structure

```
tests/eval/
├── golden/                    # Versioned test case datasets
│   └── v2026-01-19.yaml       # Current golden dataset (50 cases)
├── rubric.yaml                # Evaluation criteria definitions
└── README.md                  # This file
```

## Overview

The evaluation dataset supports pairwise comparison between:
- **Quilto responses**: Generated by the full Quilto agent pipeline
- **Baseline responses**: Generated by Claude or other reference models

### Why Pairwise Comparison?

Research shows pairwise evaluation is more reliable than absolute scoring:
- Reduces judge model bias (~40% inconsistency mitigated with position swap)
- More consistent human-alignment
- Easier for LLM judges to make relative comparisons

## Dataset Versioning

Golden datasets are treated as release artifacts with date-based versioning:

| Version | Date | Case Count | Notes |
|---------|------|------------|-------|
| v2026-01-19 | 2026-01-19 | 50 | Initial dataset |

### Versioning Strategy

1. **New versions** are created when:
   - Test cases are added or removed
   - Evaluation criteria change significantly
   - Context entries are updated

2. **Version format**: `vYYYY-MM-DD.yaml`

3. **Backwards compatibility**: Old versions are preserved for historical comparison

## Test Case Categories

| Category | Count | Description |
|----------|-------|-------------|
| simple | 3 | Basic single-question queries |
| complex | 4 | Multi-step or comparison queries |
| insufficient | 3 | Queries with data gaps |
| retrieval | 10 | Retrieval strategy effectiveness |
| reasoning | 10 | Multi-step reasoning quality |
| edge | 10 | Boundary and ambiguous cases |
| domain | 10 | Domain expertise demonstration |
| **Total** | **50** | |

## Rubric Criteria

See `rubric.yaml` for detailed scoring guidance. Four criteria are evaluated:

1. **accuracy**: Factual correctness based on retrieved data
2. **completeness**: All aspects of query addressed
3. **conciseness**: No unnecessary verbosity
4. **domain_expertise**: Appropriate fitness terminology and knowledge

## Test Case Format

Each test case in the golden dataset includes:

```yaml
- id: "unique-identifier"
  category: "simple|complex|insufficient|retrieval|reasoning|edge|domain"
  query: "The user query text"
  context_entries: ["2019-01-28", "2019-02-01"]  # Dates from corpus
  rubric_criteria: ["accuracy", "completeness"]  # Which criteria apply
  evaluation_hints:
    should_mention: ["specific elements"]
    should_not: ["things to avoid"]
```

## Context Entries Source

Context entries reference dates from `tests/corpus/fitness/entries/from_csv/`. These are real workout logs derived from Strong CSV data, written in Korean.
